# Stage A — Stop COLLIE404 in Vite/React/Next/Angular projects (vanilla-only diagnostic gate)

**Repo:** `collie-vscode`

This is the error:

> Template id "AppComponent" has no matching HTML placeholder… (COLLIE404)

That diagnostic must only fire when the extension decides the project is **“vanilla HTML placeholder mode.”** Right now the extension is incorrectly applying that rule inside framework projects.

### Codex prompt

```md
## Context & Problem

In `collie-vscode`, the diagnostic COLLIE404:

"Template id <X> has no matching HTML placeholder. Add id="<X>-collie" to your HTML to render this template. (COLLIE404)"

is intended ONLY for vanilla HTML projects (static entry HTML placeholder rendering).

However, it is currently being emitted in a Vite + React project whenever a `.collie` file contains `#id ...`.

That MUST NEVER happen for framework projects (Vite/React/Next/Angular/etc.).

## Goal

Make COLLIE404 vanilla-only:

- ✅ Emit COLLIE404 ONLY when the project is detected to be vanilla HTML placeholder mode
- ❌ Never emit it for Vite, React, Next.js, Angular, or any non-vanilla mode
- Preserve existing behavior for actual vanilla HTML projects

## Where to work

Find where COLLIE404 is produced/emitted in the extension diagnostics pipeline, likely under:
- `src/features/diagnostics/*`
- `src/diagnostics/*`
- or wherever `.collie` documents are validated

Then locate what logic determines "requires HTML placeholder".

## Implementation Requirements

- Use the SMALLEST change possible: a guard/short-circuit.
- If project-type detection exists already (e.g. adapter/mode flag), reuse it.
- If not, implement minimal project detection using existing signals:
  - presence of `vite.config.*`, `next.config.*`, `angular.json`, etc.
  - or package.json deps (react, next, @angular/core, vite, etc.)
  - DO NOT add heavy scanning; keep it cheap/cached.

## Acceptance Criteria

- In a Vite+React repo: any `.collie` file with `#id AppComponent` produces NO COLLIE404.
- In a vanilla HTML repo: COLLIE404 still appears when placeholder is missing.
- No other diagnostics change.

## Do NOT write tests

Briefly explain what was mis-scoped and what guard you added.
```

# Stage B — Allow attributes after tags (same-line and indented “attribute lines”) without COLLIE004

**Repo:** `collie-vscode`

You’re hitting:

> “Element lines may only contain .class shorthands or inline text after the tag name. (COLLIE004)”

That message is coming from the extension’s parser rules. You want **all of these** to parse:

### same-line attributes

```collie
a href="https://react.dev" target="_blank" img.logo.react src={reactLogo} alt="React logo"
```

### indented attribute lines (your “inconsistent but allow it for now” style)

```collie
a
  href="https://vite.dev" target="_blank" img.logo src={viteLogo} alt="Vite logo"
```

Right now, extension parsing is basically:
`tag(.class...)? (| inlineText)?` and **nothing else**.

### Codex prompt

```md
## Context & Problem

The VS Code extension parser currently throws COLLIE004 if an element line contains anything after the tag name other than:
- `.class` shorthands
- or inline text beginning with `|`

This rejects valid/desired authoring patterns such as:
- Same-line attributes: `a href="..." target="_blank" img.logo ...`
- Indented attribute lines under an element:
  `a` newline `  href="..." ...`
- Mixed shorthand classes + attributes on the same line

We want to allow this syntax NOW (rules/config later).

## Goal

Update the extension parser so element headers can accept:
1) `.class` shorthands (existing)
2) Attribute-like tokens (`name=...`) after tag name and/or after `.class`
3) "Indented attribute lines" directly under an element (same indentation rules as children), treated as attributes for the parent element
4) Preserve existing inline text rules (`| text`)

IMPORTANT: This change is to stop false parser diagnostics in the editor.

## Examples that MUST parse without COLLIE004

Example 1:
div
  a
    href="https://vite.dev" target="_blank" img.logo src={viteLogo} alt="Vite logo"
  a href="https://react.dev" target="_blank" img.logo.react src={reactLogo} alt="React logo"

Example 2:
div
  a href="https://react.dev" target="_blank" img.logo.react src={reactLogo} alt="React logo"

## Where to work

Find the element-line parsing rule that throws COLLIE004, likely in:
- `src/format/parser/parse.ts` (or similarly named)
- focus on `parseElement()` or the function that processes tokens after the tag name

## Implementation Notes (keep it minimal)

- You do NOT need full attribute AST semantics right now. It's okay to:
  - syntactically accept attribute payload and store it as raw strings,
  - OR attach it to element nodes as a list of { raw: string } entries,
  - OR even treat indented attribute lines as raw "attribute lines" for now.
- But you MUST stop emitting COLLIE004 for attribute-like tokens.
- Keep indentation behavior unchanged for real children (tags/text).

## Acceptance Criteria

- The provided examples no longer produce COLLIE004.
- Existing valid syntax still parses the same.
- Error messages should not change except COLLIE004 no longer triggers for these cases.

## Do NOT write tests
```

# Stage C — Allow “same-line text” like `p Edit` (without requiring `|`)

**Repo:** `collie-vscode`

You want:

```collie
p Edit
```

to behave like:

```collie
p
  | Edit
```

This is a syntax choice (and I get why you want it—forcing a full extra line for short content is annoying). The extension currently requires `|` to disambiguate content.

You asked for these to pass:

```collie
p Edit
  code | src/App.tsx
  | and save to test HMR
```

### Codex prompt

```md
## Context & Problem

Currently, inline text content for an element requires a `|` prefix, e.g.:
`p | Edit`

But we want to allow a shorthand form:
`p Edit`

This is intentionally permissive for now (config rules later).

## Goal

Extend element header parsing to allow "same-line text" after the element header when:
- the remainder of the line is NOT attribute-like tokens (e.g. not `name=...`)
- and NOT `.class` shorthands

Examples that must be accepted:

p Edit
p Hello world
h2 Title

And it must still support children lines below:
p Edit
  code | src/App.tsx
  | and save

## Where to work

- The same element parsing function that currently enforces only `.class` or `|` after tag name (COLLIE004 source).
- Add parsing logic that treats the remainder as inline text when it doesn't look like attributes/classes.

## Constraints

- Minimal change: do not redesign parsing.
- Keep `|` behavior as-is.
- If ambiguous cases exist (e.g., `p foo=bar`), treat as attributes not text.

## Acceptance Criteria

- `p Edit` parses with no COLLIE004 and is treated as inline text content for the `p`.
- `a href="..."` remains attributes, not text.
- Existing syntax remains unchanged.

## Do NOT write tests

## Stage B — Allow attributes after tags (inline) and indented attribute lines

**Repo:** `collie-vscode`

**Key change:** Remove Stage C entirely (don’t implement `p Hello`).

### Codex prompt (Strict Attributes + Hard Precedence)

## Context & Problem

The VS Code parser throws COLLIE004 if an element line contains anything after the tag name other than `.class` shorthands or `| inline text`.

We want to allow attributes (inline and indented-attribute-lines) BUT we want to avoid ambiguous parsing. Therefore, we are NOT adding `p Hello` shorthand yet.

## Hard Precedence Rules (MUST IMPLEMENT)

For an element header line (after the tag name):
1) `.class` shorthands are always allowed and bind to the element.
2) Attribute tokens are allowed and bind to the element.
   - Attribute token forms:
     - `name="string"`
     - `name={jsExpression}`
     - `name=true|false|number` (if you already support)
     - `img.logo` is NOT an attribute; it's a tag+class shorthand and should be handled as a child element token only if your grammar supports that. Otherwise ignore for now.
3) Inline text is ONLY allowed when prefixed by `|`.
4) Any other token after the tag name that is neither `.class`, attribute, nor `|` should remain an error (COLLIE004).

For indented lines immediately under an element:
- If the line "looks like attributes" (same attribute token rules), treat it as attributes for the parent element, until the first non-attribute child line appears.
- Once a non-attribute child starts, stop consuming attribute lines.

## Examples that MUST parse without COLLIE004

div
  a
    href="https://vite.dev" target="_blank" src={viteLogo} alt="Vite logo"
  a href="https://react.dev" target="_blank" src={reactLogo} alt="React logo"
  p
    | Edit
    code | src/App.tsx
    | and save to test HMR

## Where to work

- `src/format/parser/parse.ts` — function that parses element header lines and throws COLLIE004.

## Constraints

- Minimal, local change. Do not rewrite the whole parser.
- Do NOT implement `p Hello` shorthand in this stage.

## Acceptance Criteria

- Attribute tokens no longer cause COLLIE004.
- `p Hello` still errors unless `|` is used (intentional).
- Existing valid syntax remains valid.

## Do NOT write tests
