## High-level refactor strategy

### Guiding rules (so the refactor doesn’t devolve into “move stuff around”)

1. **Types live next to the domain that owns them**, not in a global bucket.

   * Example: `features/semanticTokens/types.ts`, not `src/types.ts`.
2. **Helpers are split by “reason to change,” not by file that used to contain them.**

   * Example: “range conversion” helpers in diagnostics should not live in `provider.ts` just because they were written there first.
3. **Keep public entrypoints stable** (or at least predictable):

   * For “modules people import”, prefer `index.ts` barrel exports.
   * Keep `src/extension.ts` and `src/features/index.ts` (or re-export from them) so activation wiring remains easy to follow.
4. **Never create a helper file that’s just a dumping ground.**

   * If `helpers.ts` in a folder starts getting big, split it into `helpers/<topic>.ts`.

# Refactor plan in manageable stages

## Stage 1 — Introduce the new “core/shared” conventions (no behavior changes)

### Goal

Establish stable places to put common helpers and core types so later stages don’t invent random new homes.

### Steps

1. Create:

   * `src/core/logger/*`
   * `src/shared/helpers/*`
   * `src/shared/types/*`
2. Move logger types out of `src/logger.ts`:

   * `Logger` interface → `src/core/logger/types.ts`
   * implementation → `src/core/logger/createLogger.ts`
   * `src/core/logger/index.ts` exports `{ createLogger }` + types
3. Keep `src/logger.ts` as a compatibility shim for now:

   * `export type { Logger } from './core/logger/types'`
   * `export { createLogger } from './core/logger/createLogger'`
   * (This avoids touching every import immediately.)

✅ Deliverable: new folders exist, logger moved, old imports still work.

🚩 Watch-out: Don’t introduce `shared/helpers/index.ts` barrels yet unless you need them; barrels are the #1 way refactors accidentally create cycles.

---

## Stage 2 — Move “top-level orchestrator” types out of `features/index.ts`

### Goal

Make `features/index.ts` read like orchestration, not definitions.

### Steps

1. Move:

   * `FeatureContext` and `FeatureRegistration` → `src/features/types.ts`
2. Extract helper:

   * `runFeature` → `src/features/helpers.ts` (activation-only helpers)
3. Keep `src/features/index.ts` as the orchestration entrypoint, but make it thin:

   * imports types + helpers
   * imports registrations
4. Update imports elsewhere:

   * Anywhere importing `FeatureContext` should import from `src/features/types`.

✅ Deliverable: activation file is easy to scan; types are segregated.

---

## Stage 3 — Semantic tokens refactor (high ROI, low external coupling)

`src/features/semanticTokens/tokenize.ts` is big and fairly self-contained. Perfect early “pattern” to replicate.

### Goal

Split tokenization into:

* types
* patterns
* comment segmentation
* token push/overlap utilities
* main tokenizer loop

### Steps

1. Move types:

   * `CollieSemanticToken` + internal types you want to formalize (`TokenizerState`, `Segment`) → `semanticTokens/types.ts`
2. Move regex patterns/constants:

   * all those `*Pattern` constants → `semanticTokens/helpers/patterns.ts`
3. Extract comment logic:

   * `computeCommentSegments` and related helpers → `semanticTokens/helpers/comments.ts`
4. Extract token building utilities:

   * `pushToken`, `clipTokenLength`, `overlaps`, etc. → `semanticTokens/helpers/tokens.ts`
5. Keep `tokenize.ts` as the “public algorithm” that composes helpers.

✅ Deliverable: `tokenize.ts` shrinks from ~600 lines to ~150–250 and becomes readable.

⚠️ Watch-out: regex `lastIndex` handling.
You have patterns using `/g` and then manually resetting `lastIndex`. When extracting, be consistent—either:

* never use `g` unless looping, OR
* always reset `lastIndex` inside the helper that uses it
  This is a classic bug source once code moves around.

## Stage 4 — Collie config refactor (big file, but boundaries are clear)

`src/config/collieConfig.ts` mixes: types, constants, caching, parsing, FS probing, and VS Code events.

### Goal

Turn `collieConfig.ts` into a facade with:

* exported API
* minimal wiring
  Everything else goes into `types.ts`, `constants.ts`, and `helpers.ts` (or split helpers later if it grows).

### Steps

1. Move the interfaces:

   * `CollieConfigParsed`, `CollieConfigFlags`, `CollieConfigResult`, `CollieConfigChange` → `src/config/types.ts`
2. Move constants:

   * filenames list, globs → `src/config/constants.ts`
3. Move internal helpers into `src/config/helpers.ts`:

   * `extractConfigFields`
   * `computeFlags`
   * cache invalidation helpers
   * `fileExists`, `findNearestConfigPath`
4. Leave `collieConfig.ts` exporting:

   * `onDidChangeCollieConfig`
   * `resolveCollieConfigForDocument`
   * any other public API
     but have it call into helpers.

✅ Deliverable: `collieConfig.ts` is mostly “API surface”.

🚩 Watch-out: caches + events.
When you move caches into helpers, ensure:

* there is still a *single* cache instance (module singleton)
* event emitter stays stable (importing multiple emitters is a subtle bug if you accidentally duplicate modules via path changes)

## Stage 5 — Template index refactor (`lang/templateIndex.ts`)

This is doing scanning, parsing, exclusion rules, debouncing, caching, eventing. It will benefit heavily from splitting, but it touches more features.

### Goal

Create `src/lang/templateIndex/` module folder with:

* `index.ts` as public API
* `types.ts`
* helpers for scan/parse/exclude/debounce

### Steps

1. Create `src/lang/templateIndex/index.ts` and start by copying the existing `templateIndex.ts`.
2. Move `TemplateLocation` → `src/lang/templateIndex/types.ts`
3. Extract helpers:

   * `exclude.ts`: excluded directories logic
   * `parseBlocks.ts`: parse template blocks from text
   * `scan.ts`: workspace scanning, globbing, reading files
   * `debounce.ts`: debouncing utilities (or use shared `debounce.ts`)
4. Convert `src/lang/templateIndex.ts` into a shim that re-exports from `src/lang/templateIndex/index.ts` (temporary to avoid huge import churn).
5. Update imports gradually when you touch dependent files.

✅ Deliverable: your language indexing system becomes navigable.

⚠️ Watch-out: path-based keys and URI normalization.
Make sure any helper that creates map keys uses the same canonical representation everywhere (e.g., `uri.fsPath` vs `uri.toString()`).

## Stage 6 — Diagnostics refactor (largest “feature” hotspot)

Diagnostics code is big, stateful, and uses caches + scanning. It’s where bloat grows fastest.

### Goal

Split diagnostics into:

* `types.ts` for any local types
* helper modules for:

  * range/span conversion
  * directive parsing sets/regex
  * template usage scanning cache
  * debounced refresh scheduling

### Steps

1. Create `src/features/diagnostics/types.ts`

   * If you don’t have many local types today, you still create this and move any future ones here.
2. Move “range conversion” functions into `helpers/ranges.ts`:

   * `spanToRange`
   * `spanPositionToVs`
   * anything similar
3. Move directive constants into `helpers/directives.ts`:

   * `SUPPORTED_DIRECTIVES`, `DIALECT_DIRECTIVE_ALIASES`
4. Move cache invalidation and versioning into `helpers/cache.ts`:

   * template entry versioning
   * template usage versioning
5. Move template usage scanning into `helpers/templateUsage.ts`

   * patterns like `COLLIE_COMPONENT_PATTERN`, `HTML_PLACEHOLDER_PATTERN`
   * scanning workspace logic (if it’s currently embedded)
6. Leave `provider.ts` primarily responsible for:

   * VS Code integration
   * orchestrating calls into helpers

✅ Deliverable: diagnostics reads like “control flow”, not a wall of utility code.

🚩 Watch-out: hidden coupling via module-level variables.
When splitting, decide explicitly:

* what state stays in provider (most stable)
* what state moves into helper modules (only if it’s truly internal)
  Too much shared module state across helper files becomes harder to reason about than the original file.

## Stage 7 — Conversion refactor

Conversion has multiple command files + writer + selection converter.

### Goal

Stop repeating “document selection parsing / edits / file writes” patterns across files and centralize them.

### Steps

1. Create `src/features/conversion/types.ts`:

   * move `CollieWriteResult`, `CollieTemplateMatch`, `CollieTemplateBlock` out of `collieFileWriter.ts`
2. Create `src/features/conversion/helpers.ts` for shared conversion helpers:

   * common URI/file writing
   * normalization of line endings
   * consistent error wrapping/logging
3. Reduce `convertSelectionCommand.ts`:

   * selection parsing → helper
   * conversion orchestration stays in main command file

✅ Deliverable: conversion code becomes “lego bricks” rather than bespoke.

## Stage 8 — Format parser split (the big one)

`src/format/parser/parse.ts` is ~1500 lines. That’s the biggest single bloat risk in the repo.

### Goal

Break it into internal modules without changing public API:

* Keep `parse.ts` exporting `parse(...)` (or whatever is exported now)
* Move internals into `parser/helpers/*`
* Move `ParseResult` (and parse-only types) to `parser/types.ts`

### Steps (pragmatic order)

1. Add `src/format/parser/types.ts`

   * Move `ParseResult` out of `parse.ts` into `types.ts`
2. Create “low-risk extraction buckets” first:

   * `helpers/whitespace.ts`: indentation, trimming, scanning spaces
   * `helpers/errors.ts`: diagnostic creation, error codes
3. Next extract “tokenization / lexical scanning”:

   * `helpers/lexer.ts`
4. Extract directive parsing:

   * `helpers/directives.ts`
5. Extract node constructors / AST glue:

   * `helpers/nodes.ts`
6. Keep `parse.ts` as orchestration + exports.

✅ Deliverable: parser becomes maintainable without re-architecting it.

⚠️ Watch-out: performance + allocations.
When extracting helpers, avoid creating tons of intermediate arrays/strings in hot paths. Prefer passing around indices and referencing the original string.

# Extra recommendations (worth doing while you’re in here)

### 1) Stop relying on implicit “global regex state”

Anywhere you do:

* `pattern.exec(...)` + `pattern.lastIndex = 0`
  strongly consider wrapping that in a helper so nobody forgets the reset when code moves.

### 2) Standardize “document key” strategy

Across config/lang/diagnostics you use maps keyed by paths/URIs. Pick **one canonical form**:

* `uri.fsPath` for file-only keys
* `uri.toString()` when scheme matters

Then put a helper in `shared/helpers/uri.ts` like `getFileKey(uri)`.

### 3) Use a shared debounce helper

You repeatedly use `Map<string, ReturnType<typeof setTimeout>>` patterns. Put a “debounce by key” utility in `shared/helpers/debounce.ts`. It will remove dozens of lines across lang/diagnostics/template index.
